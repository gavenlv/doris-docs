## 一、技术栈总览

| 层级 | 组件 | 本地模式 (k8s-local) | 生产模式 (k8s-gke) |
|------|------|----------------------|---------------------|
| **容器编排** | Kubernetes | Docker Desktop 内置 (1.34) | GKE (1.28+) |
| **Doris 核心** | FE (Frontend) | ✅ 3 副本 | ✅ 3 副本 |
| | BECN (Backend Compute Node) | ✅ 3 副本 (HA) | ✅ 3+ 副本 (HA) |
| | MetaService | ✅ 3 副本 | ✅ 3 副本 |
| | Doris Operator | ✅ | ✅ |
| **存储** | FoundationDB | ✅ MetaService 元数据 | ✅ MetaService 元数据 |
| | MinIO (S3 兼容) | ✅ BE 数据存储 | ❌ (使用 GCS) |
| | Local PV / host-path | ✅ | ❌ |
| | Regional PD (SSD) | ❌ | ✅ FE 元数据 |
| | GCS (对象存储) | ❌ | ✅ BE 数据 |
| **监控** | Prometheus | 可选 | ✅ |
| | Grafana | 可选 | ✅ |
| **镜像仓库** | Nexus | 可选 | 可选 |

> **架构说明**：本地模式与 GKE 模式采用**相同的存算分离架构**，仅存储后端不同：GKE 使用 GCS，本地使用 MinIO。两套方案接口一致，方便本地调试后直接部署到生产环境。

## 二、组件职责详解

### 2.1 Kubernetes 基础组件

#### Kubernetes Master

| 项目 | 说明 |
|------|------|
| **是什么** | Kubernetes 集群的控制平面节点 |
| **包含组件** | API Server、Scheduler、Controller Manager、etcd |
| **谁管理** | GKE 自动管理 / Docker Desktop 自动管理 |
| **本地模式** | Docker Desktop 单节点 all-in-one |
| **生产模式** | GKE Managed，3+ 控制平面节点 |

#### etcd

| 项目 | 说明 |
|------|------|
| **是什么** | 分布式键值存储，Kubernetes 的"大脑" |
| **存储内容** | 集群状态、Pod 定义、Service 路由、RBAC 策略 |
| **与 Doris 的关系** | 仅用于 Kubernetes 自身，与 Doris 内部状态无关 |
| **本地模式** | Docker Desktop 内置单节点 etcd |
| **生产模式** | GKE 自动复制 3 份 |

#### API Server

| 项目 | 说明 |
|------|------|
| **是什么** | Kubernetes 集群的统一 REST API 入口 |
| **Doris Operator 依赖方式** | Operator 通过 API Server 监听 DorisCluster CRD 变化，创建/更新/删除 FE/BE Pod |
| **认证方式** | ServiceAccount + RBAC |

#### Scheduler

| 项目 | 说明 |
|------|------|
| **是什么** | 决定 Pod 应该调度到哪个节点 |
| **Doris 中的作用** | 根据资源请求 (CPU/内存) 将 FE/BE Pod 调度到合适的节点 |
| **本地模式** | 默认调度器 |
| **生产模式** | 可配合污点/亲和性确保 FE/BE 分散到不同节点 |

### 2.2 Doris 核心组件

#### FE (Frontend) — 前端协调节点

```
┌─────────────────────────────────────────────────────┐
│                     FE Process                       │
│                                                      │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │  MySQL Server│  │  Thrift     │  │  HTTP     │ │
│  │  (Port 9030) │  │  Server     │  │  Server   │ │
│  │  客户端连接   │  │  (RPC 9020) │  │  (8030)   │ │
│  └──────┬───────┘  └──────┬───────┘  └─────┬─────┘ │
│         │                  │                 │        │
│         └──────────────────┼─────────────────┘        │
│                            ▼                          │
│  ┌─────────────────────────────────────────────────┐ │
│  │              Query Coordinator (QC)             │ │
│  │  1. SQL 解析 (Parser)                           │ │
│  │  2. 查询规划 (Planner)                          │ │
│  │  3. 查询调度 (Scheduler) → 分发到 BE            │ │
│  │  4. 结果合并返回                                │ │
│  └──────────────────────┬──────────────────────────┘ │
│                          ▼                           │
│  ┌─────────────────────────────────────────────────┐ │
│  │           Tablet Leader (元数据管理)             │ │
│  │  • 表结构 / 用户权限 / 分区信息                  │ │
│  │  • Tablet → BE 映射表                           │ │
│  │  • BDB JE 复制 (Leader-Follower)               │ │
│  └──────────────────────┬──────────────────────────┘ │
│                          ▼                           │
│  ┌─────────────────────────────────────────────────┐ │
│  │              DorisCatalog (元数据)              │ │
│  │  • 存储在 doris-meta 目录                       │ │
│  │  • 包含 DB/Table/View/用户/资源定义             │ │
│  └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

| 项目 | 说明 |
|------|------|
| **进程名** | `apache-doris-fe` |
| **核心职责** | SQL 解析、查询规划、查询调度、元数据管理 |
| **监听端口** | 9030 (MySQL 协议)、8030 (HTTP/Web UI)、9020 (RPC)、9010 (EditLog) |
| **元数据存储** | 本地磁盘 `$DORIS_HOME/doris-meta/`（类似 MySQL data dir） |
| **高可用机制** | Leader-Follower + BDB JE 复制（类似 Raft） |
| **写入口** | 仅 Leader FE 可写入 |
| **读出口** | 任意 FE 均可接收查询 |
| **副本数要求** | 奇数 (1/3/5)，保证选举成功 |
| **本地模式配置** | 1 副本，emptyDir 存储 |
| **生产模式配置** | 3 副本，Regional PD 持久化存储 |

**为什么 FE 需要持久化存储？**
FE 存储 Doris 的元数据（库表定义、用户权限、分区路由等）。如果元数据丢失，整个集群无法恢复，因为 Doris 没有独立的外部 Metastore（不像 Hive 需要 Metastore DB）。

#### BECN (Backend Compute Node) — 后端计算节点（存算分离）

```
┌─────────────────────────────────────────────────────┐
│                     BE Process                       │
│                                                      │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │  DorisSe     │  │  BePort     │  │  Brpc     │ │
│  │  (存储引擎)  │  │  (9050)     │  │  (8060)   │ │
│  │              │  │  Arrow Flight│  │  BE间通信  │ │
│  └──────┬───────┘  └──────────────┘  └───────────┘ │
│         │                                            │
│         ▼                                            │
│  ┌─────────────────────────────────────────────────┐ │
│  │              Storage Engine (列式存储)           │ │
│  │  • Segment: 列式数据文件 (.dat)                 │ │
│  │  • Page: 最小读取单元 (16KB)                     │ │
│  │  • Rowset: 一次写入的数据集合                    │ │
│  │  • Tablet: 数据的逻辑单元 (一个表 = 多个 Tablet) │ │
│  └──────────────────────┬──────────────────────────┘ │
│                          ▼                           │
│  ┌─────────────────────────────────────────────────┐ │
│  │           Vectorized Execution Engine           │ │
│  │  • 向量化执行：按列批量处理数据                  │ │
│  │  • 谓词下推：在 BE 过滤数据，减少网络传输        │ │
│  │  • 聚合下推：预聚合在 BE 完成                    │ │
│  │  • Join Reorder：优化多表 Join 顺序             │ │
│  └──────────────────────┬──────────────────────────┘ │
│                          ▼                           │
│  ┌─────────────────────────────────────────────────┐ │
│  │              Cache Layer (多级缓存)              │ │
│  │  • Page Cache: 热点数据页 (内存)                  │ │
│  │  • Chunk Pool: 并行执行内存池                    │ │
│  │  • Disk Cache: 本地 SSD 缓存 (生产 GKE)          │ │
│  └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

| 项目 | 说明 |
|------|------|
| **进程名** | `apache-doris-be` |
| **核心职责** | 数据计算（不存储数据）、列式读取、查询执行 |
| **与 BE 的区别** | BECN 是存算分离架构的计算节点，**不存储数据**；数据存在 MinIO/GCS |
| **监听端口** | 9060 (BE RPC)、9050 (Heartbeat)、8040 (HTTP)、8060 (bRPC)、9070 (Arrow Flight SQL) |
| **存储格式** | 列式存储 (Segment file, .dat)，支持 ZSTD/LZ4 压缩 |
| **本地模式配置** | 1 副本，MinIO 对象存储 + 本地 SSD 缓存 |
| **生产模式配置** | 3+ 副本，MinIO/GCS 对象存储 + 本地 SSD 缓存热数据 |

**为什么 BECN 不存储数据？**
- 存算一体：BE 既是计算节点又是存储节点，扩缩容时需要迁移数据
- 存算分离：计算和存储独立扩缩容，BECN 可以快速水平扩展，不影响数据

**数据流**：查询执行时，BECN 从 MinIO/GCS 读取数据 → 计算 → 返回结果。

#### MetaService — 存算分离元数据服务

| 项目 | 说明 |
|------|------|
| **是什么** | 存算分离架构下的**内部元数据管理服务**，不对外暴露 API |
| **核心依赖** | FoundationDB（作为底层元数据存储引擎） |
| **存储内容** | Tablet 元数据位置、计算节点注册信息、存储卷映射、事务状态 |
| **是否必须** | 仅在**存算分离模式**（storage-compute separation）下才需要；本地共享存储模式不需要 |
| **高可用设计** | 无状态服务，主备（Leader/Follower）模式部署 |
| **部署方式** | 通过 DorisCluster CRD 的 `spec.metaService` 字段由 Doris Operator 自动管理 |
| **通信端口** | 默认 5000（BRPC），内部使用 |
| **与 FE 的区别** | FE 管理 SQL 元数据（DorisCatalog）；MetaService 管理 Tablet/副本位置等存储层元数据 |

**为什么需要 MetaService（存算分离场景）**：

在存算一体架构中，FE 直接知道每个 Tablet 分布在哪些 BE 节点上（通过 BE 心跳汇报）。但在存算分离架构中，BE 只挂载远程对象存储（GCS/Azure Blob），不再本地存储数据文件，因此需要**独立的元数据服务**来追踪：
- 哪些 Tablet 的数据在哪个对象存储路径
- 计算节点（CN）注册和健康状态
- 数据版本和事务状态

> **注意**：本项目的 `k8s-local` 和 `k8s-gke` 默认配置均为**存算分离模式**（FE + BECN，数据存在 MinIO/GCS），启用 MetaService。存算一体模式（FE + BE 本地存储）不再作为默认配置。

#### Doris Operator — Kubernetes 控制器

| 项目 | 说明 |
|------|------|
| **是什么** | Kubernetes 自定义控制器，监听 DorisCluster CRD 并调谐集群状态 |
| **工作原理** | 调谐循环 (Reconcile Loop)：读取 DorisCluster 期望状态 → 对比实际状态 → 执行操作使两者一致 |
| **管理内容** | FE/BE/CN 的 Deployment/StatefulSet、Service、PodDisruptionBudget、扩容升级 |
| **与 FE/BE 的区别** | Operator 是"管理员"，FE/BE 是"执行者" |
| **版本** | 本项目使用 v1.4.0 |
| **部署位置** | `doris-operator-system` 命名空间 |
| **CRD 版本** | `doris.apache.com/v1`（Apache Doris Operator v1.x） |

**Operator 的工作流程**：
```
用户 apply doriscluster.yaml
         │
         ▼
DorisCluster CR 写入 etcd
         │
         ▼
Operator 监听到 CR 变化
         │
         ▼
Operator 创建 FE StatefulSet + Service
         │
         ▼
FE Pod 启动，FE 之间选举 Leader
         │
         ▼
Operator 创建 BE StatefulSet + Service
         │
         ▼
BE Pod 启动，向 FE 注册
         │
         ▼
集群 Ready
```

#### CN (Compute Node) — 纯计算节点（可选）

| 项目 | 说明 |
|------|------|
| **是什么** | 仅负责计算的节点，不存储数据 |
| **使用场景** | 弹性查询扩容，适合 Warehouse 场景 |
| **与 BE 的区别** | BE = 存储 + 计算；CN = 仅计算 |
| **依赖** | 必须有 BE 存储数据，CN 负责将查询下推到 BE |
| **本项目** | 配置文件中有预留字段，当前未启用 |

### 2.3 存储组件

#### emptyDir — 临时存储（本地模式使用）

| 项目 | 说明 |
|------|------|
| **是什么** | Kubernetes 临时存储卷，Pod 删除后数据丢失 |
| **实现** | Docker Desktop 中使用宿主机的临时目录 |
| **用途** | 仅适合开发/测试，Pod 重启后数据丢失 |
| **性能** | 等同于宿主机磁盘，Docker Desktop 场景较快 |

#### host-path — 宿主机路径映射

| 项目 | 说明 |
|------|------|
| **是什么** | 直接映射容器内路径到宿主机文件系统路径 |
| **风险** | Pod 调度到不同节点时路径不存在；权限问题 |
| **本地开发** | 可用，生产不推荐 |
| **StorageClass** | `doris-fe-storage` / `doris-be-storage` (kubernetes.io/host-path) |

#### Regional PD (Persistent Disk) — 区域块存储（GKE 生产使用）

| 项目 | 说明 |
|------|------|
| **是什么** | GCP 的区域级持久化块设备，数据在区域内的多个可用区复制 |
| **用途** | FE 元数据存储（必须持久化） |
| **性能等级** | SSD (pd-ssd)，高 IOPS |
| **容量** | 本项目配置 200Gi |
| **优势** | 单节点故障不丢数据，支持动态扩容 |

#### GCS (Google Cloud Storage) — 对象存储（GKE 生产使用）

| 项目 | 说明 |
|------|------|
| **是什么** | GCP 的对象存储服务，S3 兼容 API |
| **用途** | BE 冷数据存储（存储计算分离架构） |
| **访问方式** | 通过 `be.conf` 中的 S3 配置连接到 GCS |
| **成本** | 比 SSD 低 10x，适合存储大量历史数据 |
| **配置位置** | `k8s-gke/configmap-be.yaml` 中的 S3 相关配置 |

#### MinIO — S3 兼容对象存储（k8s-local 实际部署）

| 项目 | 说明 |
|------|------|
| **是什么** | 开源 S3 兼容对象存储，k8s-local 本地模式的数据存储后端 |
| **本项目状态** | `k8s-local` 通过 `minio-statefulset.yaml` 实际部署 MinIO StatefulSet |
| **与 GKE 的关系** | GKE 版本使用 GCS，本地版本使用 MinIO；两者接口完全一致 |
| **访问地址** | `http://minio.foundationdb.svc.cluster.local:9000` |

> **部署方式**：MinIO 以 StatefulSet 单节点模式部署在 `foundationdb` 命名空间，通过 `doris-disaggregated-cluster.yaml` 中的 S3 配置供 BECN 使用。

### 2.5 核心依赖组件

#### FoundationDB (FDB)

| 项目 | 说明 |
|------|------|
| **是什么** | 分布式事务数据库，Apple 开源 |
| **Doris 中的用途** | **存算分离模式下 MetaService 的底层元数据存储** |
| **被谁使用** | MetaService |

| **本项目状态** | 通过 `fdb-operator.yaml` 和 `fdbcluster.yaml` 部署 |

#### MinIO — S3 兼容对象存储

| 项目 | 说明 |
|------|------|
| **是什么** | 开源 S3 兼容对象存储，Amazon S3 的自托管替代方案 |
| **本项目中的角色** | **Doris BECN 的数据存储后端**（替代 GCS/GKE 版本） |
| **存储内容** | BE 数据文件（Tablet、Segment 等列式存储文件） |
| **版本** | RELEASE.2024-01-16 |
| **访问方式** | S3 协议，`http://minio.foundationdb.svc.cluster.local:9000` |
| **Bucket** | `doris-data` |
| **凭证** | `minioadmin` / `minioadmin`（开发环境，生产务必修改） |
| **部署方式** | StatefulSet（单节点独立模式），通过 `minio-statefulset.yaml` 部署 |
| **与 GKE 的关系** | GKE 版本使用 GCS，本地版本使用 MinIO；两者接口完全一致 |

> **本地与生产一致性**：MinIO 和 GCS 都实现了 S3 API，BECN 配置完全相同（仅 `endpoint` 不同），确保本地调试通过的代码直接部署到 GKE 无需修改。

#### Nexus Repository

| 项目 | 说明 |
|------|------|
| **是什么** | 私有 Docker/ Helm 镜像仓库 |
| **本项目用途** | 存储 Doris 定制镜像（FE/BE 自定义构建版本） |
| **部署方式** | `docker-compose.yaml` 中包含 Nexus 快速启动配置 |
| **生产建议** | 使用 GCR (GCP Container Registry) 或 Artifact Registry 替代 |

#### Kafka（未包含在本项目）

| 项目 | 说明 |
|------|------|
| **是什么** | 分布式消息队列 |
| **Doris 中的用途** | Stream Load 实时数据摄入（从 Kafka 消费数据） |
| **本项目** | 未包含，如需可独立部署或使用 GCP Pub/Sub 替代 |

## 三、两种部署模式对比

### k8s-local — 本地开发模式

```
┌─────────────────────────────────────────────────────┐
│           Docker Desktop Kubernetes (单节点)          │
│                                                       │
│  ┌────────────────────────────────────────────────┐ │
│  │            doris-operator-system                 │ │
│  │                   Doris Operator Pod              │ │
│  └────────────────────────────────────────────────┘ │
│                                                       │
│  ┌────────────────────────────────────────────────┐ │
│  │              foundationdb (命名空间)              │ │
│  │   ┌──────────┐ ┌──────────┐ ┌──────────┐    │ │
│  │   │ FDB Pod  │ │MinIO Pod │ │MetaService│    │ │
```

## 六、高可用设计

### 6.1 FE 高可用 — Leader/Follower 模式

```
┌──────────────────────────────────────────────────────┐
│                  BDB JE 复制组                        │
│                                                       │
│   ┌─────────┐   ┌─────────┐   ┌─────────┐          │
│   │  FE-0   │   │  FE-1   │   │  FE-2   │          │
│   │ Leader  │◄──│Follower│◄──│Follower│          │
│   │ 写入     │   │ 同步    │   │ 同步    │          │
│   └─────────┘   └─────────┘   └─────────┘          │
│       │                              │               │
│       │    Write-Ahead Log (EditLog) │               │
│       └──────────────────────────────┘               │
│                                                       │
│  选举机制: Paxos/Raft 类协议 (BDB JE 实现)            │
│  故障转移: Leader 宕机 → Follower 重新选举            │
│  写入要求: 仅 Leader 可写入                            │
│  读取要求: 任意节点可读取 (Follower 转发或本地读)     │
└──────────────────────────────────────────────────────┘
```

**为什么需要奇数个 FE？**
BDB JE 使用 Paxos 协议进行 Leader 选举和数据同步。奇数个节点能避免"脑裂"（split-brain）问题。例如 3 个节点可以容忍 1 个节点故障，仍有多数派 (2/3) 进行选举。

### 6.2 BE 高可用 — 数据副本

```
┌──────────────────────────────────────────────────────┐
│                  Tablet 数据副本                      │
│                                                       │
│   一个 Tablet 有 3 个副本，分散在不同 BE 节点          │
│                                                       │
│   Tablet-0: [BE-0]  [BE-1]  [BE-2]                  │
│   Tablet-1: [BE-1]  [BE-2]  [BE-0]                  │
│   Tablet-2: [BE-2]  [BE-0]  [BE-1]                 │
│                                                       │
│  故障恢复: BE 宕机 → FE 检测到心跳丢失 → 自动修复     │
│           → 其他 BE 补齐副本                          │
│  读取策略: 优先读取本地副本，减少网络流量              │
└──────────────────────────────────────────────────────┘
```
